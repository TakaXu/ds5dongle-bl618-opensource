# 网页固件更新开发计划

- 日期：2026-09-26。
- 目的：将既有可行性方案展开为开发任务、依赖关系和验收标准。
- 本次修改：仅新增计划文档；未修改程序、安装 SDK、构建固件、操作硬件或推送 Git。
- 固件基线：`ds5dongle-bl618-opensource`，本地提交 `f7e36e1`。
- 网页基线：`ds5dongle-config-web-bl616`，本地提交 `168dba5`，网页 v0.2.0。
- 下文模块名、命令名、包格式及工期是方案建议，最终分区、Report ID、长度和超时参数经过验证后冻结。

## 1. 目标与首版范围

目标流程：打开自有网页 → 连接接收器 → 检查版本或选择本地升级包 → 校验目标 → 传输并安装 → 接收器重启 → 网页重新连接并确认结果。

更新对象是 **BL616/BL618 接收器应用固件**，不是索尼手柄本体固件。浏览器负责互联网下载，再通过原生 USB HID 向接收器传输；接收器首版不增加 Wi-Fi、配网和 HTTP/TLS 下载模块。

建议首先支持 **LCTech BL616、实测 4MiB Flash、FS 固件**。这是缩小验证范围的默认方案，不代表已确认用户实际开发板。之后分别扩展 HS、M0S Dock 和 Ai-M61，逐个做实机验收。

首版包含：

- 本地选择升级包、在线版本检查与下载，两者共用安装链路。
- 设备端目标、长度、完整性和发布签名验证。
- 分阶段进度、取消、超时重试、预期重启及重连确认。
- 保留基础配置、两套映射、活动槽及配对信息。
- 安装中断保护、经过验证的启动失败恢复机制及 ISP 救援文档。

后续再做差分包、压缩包、跨掉电断点续传、多设备批量升级及设备自主联网升级。普通网页更新不写 Boot2、分区表、eFuse、RF 校准及密钥区，不支持跨作者固件迁移。

## 2. 当前基础及关键问题

| 当前已确认事实 | 开发影响 |
| --- | --- |
| F6 只实现配置应用、保存、重启，没有升级服务 | 必须配套修改设备固件 |
| F9 的 9 字节 OTA 预留区固定为零 | 不能据此判断升级能力，也不能猜测私有升级协议 |
| 已初始化 MTD/EasyFlash，配置保存已部分延迟到任务处理 | 有集成入口，但不代表 OTA API 或 Flash 并发已验证 |
| 默认 `../bouffalo_sdk` 不存在，`BL_SDK_BASE` 未设置 | 尚无已确认的本地构建环境 |
| README 要求定制 `sqlCRT/bouffalo_sdk`；脚本引用 Boot2 v8.1.8 文件名 | 必须固定 SDK 提交、工具链和实际 Boot2 哈希 |
| 网页精确匹配少数旧版本字符串，且固定 `otaSupported:false` | 新固件需要独立能力识别，不能仅放宽版本正则 |
| 网页默认轮询状态，USB 断开按普通拔出处理 | 更新需要独占事务和预期重启状态 |
| 本地服务器 CSP 为 `connect-src 'self'` | 优先同源托管固件，否则需同步处理 CSP、CORS 及重定向 |

### 2.1 分区是第一道关卡

本地 `firmware/lctech616/partition_cfg_4M_nosec.toml`：

| 区域 | 起始 | 大小 | 说明 |
| --- | --- | --- | --- |
| Boot2 | 0x000000 | 0xE000 | 普通 OTA 不改写 |
| 分区表 0/1 | 0xE000 / 0xF000 | 注释为每份 4KiB | 启动元数据须按真实 SDK 机制更新 |
| FW address0 | 0x10000 | 0x200000，2MiB | 第一个固件地址 |
| FW address1 | 0x210000 | 0x168000，1440KiB | 第二个固件地址 |
| mfg | 0x210000 | 0x168000 | 与 FW address1 完全重叠，用途待确认 |
| media | 0x378000 | 0x71000 | 未证明可以挪作升级区 |
| PSM / KEY / DATA / factory | 0x3E9000 起 | 各自固定区间 | 保留并核查实际用途 |

这是仓库配置，不是板上 Flash 读回结果。存在两个地址不等于具备可用 A/B 回滚；不能先删除 mfg 条目或直接擦写该区域。

必须确定当前活动区、mfg 复用约定、Boot2 镜像头、镜像偏移和净容量。若直接交替启动，镜像必须适合每次目标槽位，1440KiB 也不是净代码容量。以真实构建产物为准，不把 README 的“约 800KB”作为尺寸保证。

如果需要修改分区或 Boot2，放入首次 ISP 基线安装流程，单独备份和恢复允许保留的数据，不在日常网页升级中隐式迁移。

## 3. 总体架构及首要原则

```mermaid
flowchart LR
  R[同源版本清单与升级包] --> W[配置网页]
  F[本地升级包] --> W
  W -->|USB WebHID| U[升级协议入口]
  U --> Q[有界队列与升级任务]
  Q --> S[非活动镜像区或已验证暂存区]
  S --> V[读回哈希/签名/启动格式验证]
  V --> B[可靠提交启动元数据]
  B --> T[重启/试启动/确认或恢复]
  T -->|版本及启动结果| W
```

先完成本地包闭环，再接在线下载。网页 UI 依赖设备已确认的进度；USB 请求成功只代表传输层接收，不代表 Flash 已写完，更不代表新固件已正常启动。

分别定义“传输完成”“镜像校验与提交完成”“启动确认成功”，不得用传输 100% 代替最终成功。

## 4. P0：可复现构建与首次线刷基线

预计 2–4 人日。

任务：

1. 确认首测板型、芯片、Flash、原生 USB 接口、当前固件及 FS/HS；确认 BOOT/ISP 接线。
2. 获取定制 SDK 并固定提交，记录工具链版本、构建参数、Boot2 和分区模板哈希。
3. 构建原版，保存 ELF、map、bin、镜像尺寸、RAM/TCM 分布、堆余量及栈高水位。
4. 修复 `build_windows.bat` 的错误传播：每次 `call :build_one` 检查返回码，FS 失败不继续假装双版本成功，复制产物失败也返回非零。核对其他脚本同类问题。
5. 在测试板验证原版启动、HID、配置读写、映射、音频及重启。
6. 备份必要 Flash/配置并演练 ISP 恢复。包含配对密钥的板级备份只在本地保管，不放进公开仓库或通用发布包。

交付：环境和依赖锁定记录、原版构建产物、资源预算、串口日志、恢复指南。

**验收 G0：原版能构建和启动，构建失败可靠返回非零，测试板可通过 ISP 恢复。** 缺 SDK、测试板或恢复路径时，不进入写 Flash 阶段。

## 5. P1：分区、启动链与失败恢复

预计 3–6 人日；额外 Boot2 改造另估。

任务：

1. 读回真实 Flash 信息及分区表，核对当前活动镜像与 mfg 用途。
2. 阅读固定 SDK 的 MTD、分区更新、镜像包装和 Boot2 实现，确定直接切槽还是暂存后复制。
3. 用两个可区分的测试版本验证候选区写入、校验、提交和启动。
4. 确认 Boot2 是否支持试启动、失败次数、看门狗及成功确认；不支持则提出最小扩展或独立恢复方案。
5. 定义持久化更新记录：已确认镜像、候选镜像、pending 状态、尝试次数、回退原因。采用验证过的双副本或日志机制，避免每个 USB 分片都写元数据。
6. 定义配置迁移和回退兼容策略，试启动尚未确认时不做不可逆配置迁移。

必须分别证明两种保证：

- **安装过程保护**：未接收完整、未通过校验或未可靠提交的镜像不能被启用；提交中断仍有有效启动路径。
- **启动失败恢复**：镜像格式和哈希正确但应用死循环、关键任务创建失败或 USB 管理不可用时，设备回到旧确认镜像或独立恢复模式。

第二项不能由网页、SHA-256 或双分区地址自动实现。内部原型可以标明只提供 ISP 救援，但不能宣称自动回滚；公开稳定版必须落实选定的启动失败恢复保证。

设备健康确认至少覆盖关键初始化、必要任务创建、USB 管理可服务及稳定性检查。由设备自主确认，不能依赖网页一直开着，也不能要求手柄必须在线。确认时间窗口和失败次数按实测冻结。试启动期间还要保证管理 USB 不受旧 stealth 配置影响而消失。

交付：真实分区图、镜像格式约束、启动状态图、失败恢复实验、Boot2 复用或改造结论。

**验收 G1：备用区用途明确；提交中断、坏镜像和试启动失败均有可演示的恢复结果。** G1 之前不冻结包格式，不接受主机传入任意物理写地址。

## 6. P2：升级包与 USB 协议

预计 2–3 人日。

### 6.1 升级包格式

ISP 完整线刷包与应用升级包分开。应用包后缀可暂用 `.ds5ota`；若固定 SDK 已有适合的镜像格式，优先包装或复用，不假定普通 `.bin` 可直接写入候选区。

元数据至少包括：

| 字段 | 作用 |
| --- | --- |
| magic / package_format | 区分有效升级包、普通 bin 和整片 Flash 转储 |
| product_family / board_id / chip_id | 区分项目谱系和硬件目标 |
| usb_variant / layout_id / image_type | 区分 FS/HS、分区布局、应用与其他镜像 |
| firmware_version / build_id / release_sequence | 展示版本、唯一识别包、执行升级或降级策略 |
| min_bootloader / min_update_protocol | 检查运行环境 |
| config_schema / 兼容范围 | 确认升级和回退后数据可读 |
| header_length / payload_length / payload_sha256 | 长度边界、完整性 |
| signing_key_id / algorithm / signature | 设备确认发布来源 |

签名覆盖确定编码的目标元数据与镜像哈希，不能只签文件名或版本号。设备检查长度相互矛盾、加法溢出、未知格式/算法、意外尾部数据。首次实验可以先以哈希走通链路，公开发布包必须经过设备端签名验证。

签名算法根据固定 SDK 的成熟实现、资源预算和测试向量确定，不自行编写密码算法。私钥放受控发布环境，固件包含公钥；签名不等价于整机安全启动，本期不烧写安全启动或加密 eFuse。

### 6.2 传输入口和命令

优先复用 EP0 Feature Report，首版不添加 Bulk 端点。检查 DS/Edge、FS/HS 的描述符和 WebHID 可访问集合后再分配专用报告，不挪用已有配置或映射载荷。F9 保持原布局，新能力报告才是升级支持的权威依据。

可以从 63 字节 Feature 数据体验证起步，净分片须扣除协议头。63 不是 EP0 的绝对上限；是否扩大报告或引入小窗口传输取决于 SDK 缓冲、浏览器表现和实测速率。能力信息过长采用显式分页。

| 建议逻辑命令 | 职责 |
| --- | --- |
| GET_CAPS | 协议版本、产品/板型、USB变体、布局、容量、最大分片、恢复能力、稳定设备标识 |
| BEGIN | 验证目标和包头、创建会话、进入维护状态、准备目标区 |
| WRITE | 会话号、序号/偏移、有效长度、帧 CRC、镜像片段 |
| GET_STATUS | 状态、会话号、已持久化偏移、总长度、错误码、等待提示 |
| FINISH | 完整长度检查、Flash 读回哈希、签名及启动格式验证 |
| COMMIT | 仅在候选校验通过后提交启动元数据，重复调用幂等 |
| REBOOT | 候选已提交时重启，不顺带执行普通配置保存 |
| ABORT | 在允许阶段安全结束，保持有效启动路径 |
| GET_BOOT_RESULT | 运行 build_id、确认状态及回退原因 |

契约要求：

- 冻结字段偏移、宽度、字节序、填充和 CRC 算法/覆盖范围；C/JS 使用同一组黄金向量。
- 明确接口数据是否带 Report ID。当前设备有“首字节等于 ID 就跳过”的兼容逻辑，新二进制升级载荷不能依靠首字节猜边界。
- 以 `committed_offset` 为主机进度依据，USB 请求成功不是写入完成 ACK。
- 已写分片重复发送：内容相同返回相同确认，内容不同报错；不能重复擦除已确认页。未来偏移、旧会话、越界数据直接拒绝。
- 首版一个待确认分片或小窗口；明确 BUSY、退避、各阶段超时和最大重试。ACK 丢失先查状态再决定重发。
- 同会话且设备未重启的断连可查询偏移继续；跨掉电续传不作首版承诺，断电后从头开始。
- 错误区分目标错误、容量不足、会话失效、传输损坏、Flash 失败、签名错误、启动不兼容等。
- 查询不写 Flash；包未经目标校验前不擦除任何区。设备只安装应用包，禁止任意地址写操作。

交付：包格式与传输协议文档、C/JS 测试向量、兼容矩阵、最小收发样例。

**验收 G2：两端对同一报文的解析和拒绝结果一致，浏览器与测试固件真实收发及缓冲边界验证通过。**

## 7. P3：设备端升级服务

预计 4–7 人日，不含额外 Boot2 工程。

建议文件：

| 模块 | 责任 |
| --- | --- |
| `src/ota_protocol.c/.h` | 帧解析、能力/状态响应、长度及版本检查 |
| `src/ota_service.c/.h` | 会话、状态机、幂等、超时及取消 |
| `src/ota_storage.c/.h` | 分区范围、擦除、页写入、读回 |
| `src/ota_image.c/.h` | 镜像头、哈希、签名与启动格式校验 |
| `src/ota_boot.c/.h` | SDK/Boot2 适配、候选提交、启动确认与结果 |

建议状态：`IDLE → PREPARING → RECEIVING → VERIFYING → VERIFIED → PENDING_BOOT → TRIAL_BOOT → CONFIRMED`。异常包含 `ABORTING / ERROR / ROLLED_BACK / RECOVERY`，明确每个状态允许的命令。COMMIT 之后的取消不等于撤销升级。

集成任务：

1. `usb_gamepad.c` 新增描述符和协议分发。回调只做有界解析及复制入队；不能在回调全片擦除/哈希，也不能把 EP0 临时缓冲指针留给任务稍后使用。
2. `main.c` / `state_mgr.*` 建立维护状态。开始前处理已有保存请求；期间阻止普通配置/映射写、重启、清配对、休眠、stealth 延迟断开及重连逻辑干扰。
3. 协调音频和蓝牙：静默普通业务输出或停止相关提交，保持管理通道可服务；不能简单停音频任务却留下活跃等时端点无限积压。
4. 统一 Flash 互斥，覆盖配置、映射、蓝牙 settings 等写入。仅暂停网页轮询不足以避免设备后台竞争。
5. 验证 XIP 擦写时的 SRAM/TCM 调用链、常量、cache、中断和看门狗要求。现有 Opus 已放入 TCM，需要真实 map 和堆栈预算；使用固定有界缓冲，不整包载入 RAM。
6. 测量擦除阶段对 USB 的影响，采用分段操作和背压。单独开 OTA 任务并不自动消除 USB 超时。
7. 所有写地址由设备的分区适配计算，禁止覆盖当前有效镜像或持久化区。
8. FINISH 从实际 Flash 读回计算哈希，验证签名与启动格式后才允许 COMMIT。
9. 新固件先处理 pending 状态并核查必要任务启动；确认前避免不可逆数据迁移。
10. 取消/错误明确恢复普通业务或提示需要重启；预期重启不复用带隐式 config_save 的普通重启流程。

交付：可首次线刷的升级基线、升级服务、模拟 Flash 测试、串口日志及资源差异记录。

**验收 G3：本地包经浏览器完成真实写入和启动，两版固件可轮换，损坏包不能提交，取消/传输中断保持有效启动路径。**

### 8.1 兼容和识别

旧版支持配置的固件继续正常使用配置功能，更新页提示“需要先线刷升级基线”，不发送未知擦写命令。

新固件检查描述符、能力 magic、协议版本、产品族、板型和布局，不能只靠 Sony VID/PID 或 DS5 名称。升级能力与配置 schema 分开：支持更新但配置结构不支持时仍可安全进入更新流程，绝不使用旧偏移写配置。

使用稳定设备标识、目标 build_id 和会话记录匹配重连，多个接收器时不选择列表第一个。用户关闭 USB 序列号时也需要可靠识别策略。

### 8.2 用户操作顺序

1. 连接后读取当前版本、板型、升级/恢复能力及容量。
2. 检查在线版本或选择本地包，显示目标、变更说明、大小和兼容结果。
3. 在电脑完成下载及预校验后才进入设备维护状态，避免网络慢造成长时间暂停。
4. 检查未保存编辑，明确让用户保存或放弃，不静默写入或丢弃。升级期间锁定配置/映射写和普通重启入口。
5. 显示准备、传输、校验、提交、等待重连和确认，各阶段真实反馈。传输进度用设备已持久化字节数；无法量化的阶段展示状态。
6. 处理预期断连并保留上下文；超时显示“尚未确认结果”，不直接判成功。
7. 优先发现已授权设备；权限不覆盖新枚举时提供用户点击重新连接，不假定绕过授权。
8. 同一设备回报目标 build_id、版本及 CONFIRMED 后才显示成功；回到旧版本则展示回退原因。

浏览器刷新/关闭后，设备也必须能安全结束或自主确认启动。`beforeunload` 只作提醒，不作为安全保证。跨标签互斥是辅助，设备端会话锁才是最终保护。

备份：当前 JSON 只含基础配置，建议扩展为基础配置、两个映射槽和活动槽，并记录 schema；不导出蓝牙配对密钥。恢复前核对兼容性，升级正常路径仍以保留原持久化区为主。

**验收 G4：模拟旧固件、损坏包、忙/超时、断连、成功和回退，UI 判断准确；实机完成本地包闭环；现有配置、映射和测试页无回归。**

## 9. P5：在线发布、签名与流水线

预计 2–4 人日。

建议目录：

```text
releases/stable.json
releases/beta.json
firmware/<不可变版本>/<板型>-<USB变体>-<build_id>.ds5ota
```

清单包括目标、版本、build_id、布局及协议要求、包大小/哈希、下载地址、发布说明、通道及撤回状态。包自身的认证元数据决定能否安装，清单负责发现和展示。

任务：

1. 固件仓库添加包生成、检查与签名脚本，分别产出 ISP 基线包和日常应用 OTA 包。
2. 从构建参数自动生成板型、FS/HS 和布局标记，禁止简单重命名 bin 作为其他板型包。
3. 优先同源静态托管；GitHub Releases 可归档，直接浏览器下载则实测资产重定向、CORS、限流及错误返回，不能假设总能 fetch。
4. 使用不可变包地址，清单采用重新验证策略。先上传并验证固件，再更新通道清单，避免清单指向未就绪资产。
5. CI 运行协议、包格式、尺寸、签名和构建检查；任何失败不得沿用旧产物发布成功。网页与固件发布依赖分开。
6. beta/stable 分离，稳定发布只列出通过实机验收的板型。无需首版就建立账户系统或动态后台。
7. 私钥保存在受控发布环境；管理 key_id、公钥轮换与版本撤回。网页不持有私钥，不声称修改清单能撤回已安装版本。
8. 明确同版本重装、手动降级与自动回退策略；防降级规则不能阻断既定失败恢复。首版不写不可逆防回滚 eFuse。

**验收 G5：正确目标可在线获取正确包，错板/损坏/未知签名包不能安装，更新清单与缓存行为可验证，ISP 包和 OTA 包不能相互误用。**

## 10. P6：故障注入、回归与发布验收

预计 4–7 人日。

| 类别 | 场景 | 预期 |
| --- | --- | --- |
| 识别 | 真手柄、其他作者分支、旧基线、错板/芯片/变体/布局 | 拒绝升级，不擦 Flash |
| 包边界 | 空、截断、超大、长度溢出、错误头、损坏签名、额外数据 | 有明确错误，不提交候选 |
| 容量 | 接近边界、恰好边界、超出一字节 | 按完整存储布局计算并严格限制 |
| 传输 | 忙、延迟/丢失 ACK、重复/乱序块、旧会话、重复结束/提交 | 幂等和背压，无静默丢块 |
| 浏览器 | 取消、刷新、关闭、权限拒绝、多个标签/应用竞争 | 设备保留有效启动路径，不伪成功 |
| USB | 线缆拔插、Hub、换口、主机睡眠、枚举变化 | 超时和恢复明确，不串到另一设备 |
| 掉电 | 擦除、页写入、最后一页、校验、元数据提交、首次启动 | 保留有效固件或经过验证的恢复模式 |
| 启动故障 | 合法镜像早期死循环、任务创建失败、USB 不工作 | 按 P1 保证回退或恢复 |
| 配置 | 基础配置、两个映射槽、活动槽、配对、校准数据 | 升级及回退后符合保留/兼容策略 |
| 正常业务 | 输入、DS/Edge枚举、音频/麦克风、震动/扳机、休眠唤醒、stealth | 无更新模块引入的回归 |
| 压力 | 重复升级/取消、最大镜像、RAM/栈峰值、时长 | 无泄漏或越界，记录真实吞吐 |

建议首测板至少完成 20 次连续正常升级/版本交替，每个关键掉电阶段至少重复 3 次；先做确定性故障点，再做随机时刻断电。这只是工程验收门槛建议，不是可靠性统计保证。

使用可恢复测试板、串口日志和适当的供电控制，不在唯一日常设备上直接进行破坏性实验。Windows Chrome/Edge 首测；HS、其他操作系统及额外板型各自增加验证，不能由同浏览器内核推定全部通过。

**验收 G6：日志可串联包、设备、持久化偏移、候选提交及启动确认/回退；每个发布目标均有硬件证据，已知限制写入发布说明。**

## 12. 首次升级与开工输入

现有开源固件没有升级接收服务，通常必须先通过 Dev Cube/ISP 安装一次具备升级能力的基线。需要的 Boot2 或分区迁移也在这次明确的线刷流程中完成。以后日常更新才走网页，Dev Cube 仍保留首次安装和救援用途。

实施前确认：

1. 首测开发板、真实 Flash 容量、当前固件及 FS/HS。
2. 是否有可恢复测试板、串口/BOOT 接线、供电控制和原始恢复包。
3. SDK、工具链及 Boot2 精确版本，mfg 区用途。
4. 配置、映射和配对保留要求；首版默认不跨作者固件迁移。
5. 首发板型范围、固件托管域名和签名发布环境。

建议下一次实际开发先完成 **P0 和 P1**，通过后再冻结协议并实施完整网页流程。先做完善 UI 无法消除分区和启动链风险。
